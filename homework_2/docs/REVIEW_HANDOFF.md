## Найденные проблемы

P1 — блокирует воспроизводимый запуск или автономную демонстрацию; P2 — заметный недочёт
поведения/интеграции; P3 — небольшая ошибка либо улучшение, не блокирующее учебную демонстрацию.

### P1. Сборка и зависимости бэкенда не закончены — роль 4

`Dockerfile:4–5` копирует и устанавливает `requirements.role4.txt`, которого в директории нет.
В `requirements.txt` отсутствуют `fastapi` и `uvicorn`, поэтому установка только из него
не обеспечивает ни импорт `app.main`, ни запуск сервера в чистом окружении.

Минимальное решение: либо добавить отсутствующий файл с зависимостями бэкенда, либо
перенести их в общий requirements и убрать вторую ссылку в Dockerfile. `pytest` нужен
для разработки и CI. Затем действительно проверить сборку образа и запуск с volume для БД.
CI и отдельного README приложения в текущем дереве также нет, хотя они отнесены к роли 4.

### P1. Модель не доставляется вместе с приложением — роли 2 и 4

`SemanticEngine()` загружает модель лениво при первом кодировании
(`app/engines/semantic.py:98–108`), а `create_app()` не прогревает её.
Сам по себе установленный `sentence-transformers` весов модели не содержит.
Dockerfile копирует только `app/`, кэш модели в образ не помещает.

В этой проверке автономная работа удалась благодаря уже существовавшему локальному
Hugging Face-кэшу. На новом ноутбуке или в новом контейнере такого кэша может не быть:
в отсутствие сети семантический `/news` вернёт ошибку загрузки модели.

Минимальное решение: заранее загрузить модель в том же окружении/контейнере, где пройдёт
приёмка, сохранить кэш и проверить повторный запуск с `HF_HUB_OFFLINE=1`.
Для контейнера кэш хоста сам по себе недоступен: нужен отдельный mount или загрузка в образ.
SQLite с векторами не заменяет веса модели: как минимум новое описание темы всё ещё надо кодировать.
Переписывать механизм эмбеддингов ради этого не требуется.

### P2. Пакетная индексация роли 2 не подключена к бэкенду — роль 4

В `app/main.py:99` poller сохраняет только статьи. То же происходит при добавлении источника
и постинге. В `filtered_news()` вызов `semantic.match()` выполняется отдельно для каждой
статьи; `semantic.index()` нигде в бэкенде не вызывается.

Подтверждено: сразу после загрузки статей encoder не вызван ни разу; первый запрос выдачи
по 134 новым статьям сделал **134 вызова encoder по одному тексту**. При прогретой модели
этот запрос занял около **0.55 с**, повторный — **0.05 с** и ноль новых кодирований.
Загрузка самой модели — отдельная стоимость, в отдельной проверке около 6 с.
Цифры зависят от ноутбука; скорости пакетного бенчмарка нельзя приписывать текущему API.

Это не ломает небольшую демонстрацию, но расходится с обещанием «векторы пакетами при загрузке».
Небольшая доработка: для очередной пачки кандидатов сначала восстановить сохранённые векторы,
одним `index()` закодировать отсутствующие, затем сохранить их и проверять фильтры.
Для полной реализации плана это можно вынести в обработку новых статей после присвоения им ID в БД.
Не нужно пересчитывать все векторы на каждом старте.

### P2. Ошибки вычисления эмбеддингов обходят SemanticError — роль 2, исправлено

После исправления исключения encoder оборачиваются в `SemanticError` с исходной причиной;
форма, размерность и конечность векторов проверяются до попадания в кэш. Описание ниже
относится к исходной реализации.

В `semantic.py:101–105` обёрнута только загрузка модели; вызов encoder в `embed()` на
строке 115 выполняется вне этой обработки. Encoder, выбрасывающий `RuntimeError`,
оставляет наружу именно `RuntimeError`. В `main.py:214` такой тип не обрабатывается,
поэтому ошибка вычисления приводит к 500 вместо понятного ответа.

Рекомендуется оборачивать ожидаемые ошибки выполнения encoder в `SemanticError` с сохранением
исходного исключения через `raise ... from exc`. Полезно проверять форму и конечность
возвращаемых векторов, особенно при подмене encoder или чтении внешних векторов.
На нормальном пути с настоящей моделью эта проблема не проявилась.

### P2. Предпросмотр темы существует только как Python-метод — роли 4 и 5

`SemanticEngine.rank()` реализован и протестирован, но API для него нет.
Браузер не может непосредственно вызвать метод Python. Обычный `/news` отдаёт только
совпадения и скрывает оценки статей ниже порога, поэтому не заменяет полноценный предпросмотр.

Если сохраняете эту возможность из `docs/semantic.md`, добавить, например,
`POST /api/users/{u}/filters/preview`: принять ещё не сохранённую тему, выбирать только
статьи подписок этого пользователя, возвращать ограниченное число статей с оценками
независимо от порога. Это предложение, **не существующий маршрут**.
Для минимальной сдачи можно пока ограничиться изменением порога и повторным запросом `/news`.

### P2. Валидация принимает фактически пустые фильтры — роли 4 и 2

На стороне движка роли 2 пустые очищенные фразы теперь отбрасываются, неверные типы
настроек дают `SemanticError`. Приём фактически пустого фильтра через POST/PUT и пустого
имени остаётся проблемой серверной валидации роли 4.

Проверка `_validate_filter()` (`main.py:53–79`) идёт до очистки текста, а имя обрезается
через `.strip()` уже после проверки длины. Через API удалось сохранить с кодом 201:

- keyword с `{"any": ["   "]}` — фактически пустой, ничего не находит;
- topic с `{"description": "<p></p>"}` — после очистки остаётся пустая фраза;
- фильтр с именем `" "` — сохраняется с пустым именем.

Проверять непустое имя после `.strip()`, ключевые слова после токенизации, темы после
очистки. В `SemanticEngine.topic_phrases()` также стоит отбрасывать пустые уже очищенные
строки. Это особенно полезно для сценария настройки приложения человеком из аудитории.

### P2. Выдача молча ограничена первыми 10 000 кандидатами — роль 4

`main.py:195` использует `range(0, 10_000, 200)`. Более старое совпадение не попадёт
в выдачу даже при корректной пагинации. Для небольшого учебного набора не мешает;
для полноценной ленты убрать предел либо явно включить ограничение истории в контракт API/UI.
Вывод сделан по коду, отдельная загрузка 10 001 статьи не выполнялась.

### P3. index() считает прирост размера кэша вместо числа новых векторов — роль 2, исправлено

Теперь возвращается число уникальных закодированных текстов, независимо от вытеснений;
покрыты заполненный и отключённый кэш, большие пакеты и дубликаты. Ниже — исходный дефект.

`semantic.py:142–147`: `return len(self._cache) - before` работает только до заполнения кэша.
Пример: `cache_size=1`, `index([статья А])` возвращает 1, а `index([новая статья Б])`
возвращает **0**, хотя Б действительно закодирована и заменила А. При большом пакете
число тоже будет занижено. На сами результаты `match()` это не влияет; бэкенд сейчас
возвращаемое значение не использует.

Если сохранять обещанный контракт, возвращать число уникальных непустых текстов,
которых не было в кэше перед кодированием, независимо от последующего вытеснения.

### P3. Другие небольшие замечания по роли 2

- **Исправлено:** раньше `_vectors()` не обновлял порядок при чтении из кэша; вытеснение зависело от записи,
  а не последнего использования. При `cache_size=2` последовательность
  «записать А, Б → прочитать А → записать В → прочитать А» повторно кодирует А.
  Если нужен LRU, передвигать и прочитанные элементы. Для небольшого набора это несущественно.
- **Исправлено:** раньше `clean_text()` удалял теги регулярным выражением, но оставлял содержимое `script/style`:
  `<script>политика санкции</script><p>Футбол</p>` превращается в
  `политика санкции Футбол`. В штатном API RSS предварительно чистит агрегатор, поэтому
  это недостаток самостоятельного движка и обещания «HTML можно оставить», а не
  подтверждённое загрязнение текущей выдачи. Для отдельного использования нужен HTMLParser.
- Ключ сохранённого вектора — имя модели, без версии модели/настроек предобработки
  (`db.py:224–231`). При дальнейшем изменении `max_chars`, префиксов или весов под тем же
  именем нужен новый ключ/сброс старых векторов. Для текущей неизменной конфигурации работает.
- `score` — косинусное сходство, **не вероятность и не процент уверенности**.
  В режиме `mean` score относится к усреднённой теме, а `best_phrase` — лишь ближайшая
  отдельная фраза, а не полное объяснение оценки. Отразить это в интерфейсе и слайдах.

## Фактический контракт для интерфейса

Лучше держать UI и API на одном origin: добавить маршрут страницы, шаблоны и подключение
статики в FastAPI. При отдельном frontend-origin понадобится настройка CORS.

| Действие | Существующий API | Существенные детали |
| --- | --- | --- |
| Пользователи | `GET /api/users`, `POST /api/users` | Создание: `{"name":"Аня"}`; переключение профиля хранить на клиенте |
| Все известные источники | `GET /api/feeds` | Источники общие; подписки отдельные |
| Подписки | `GET/POST /api/users/{u}/feeds` | POST: `{"url":"https://..."}` **или** `{"feed_id":1}` |
| Отписка | `DELETE /api/users/{u}/feeds/{feed_id}` | Путь отличается от укрупнённого черновика PLAN.md |
| Фильтры | `GET/POST /api/users/{u}/filters`, `PUT/DELETE /api/users/{u}/filters/{f}` | PUT передаёт полное имя, kind и params |
| Новости | `GET /api/users/{u}/news?limit=50&offset=0` | Ответ — массив; limit 1–200; offset считает совпавшие статьи |
| SSE | `GET /api/users/{u}/stream` | Именованное событие **refresh**, данные `{revision,user_id}`; после события заново запросить `/news` |
| Свои каналы | `GET/POST /api/channels` | Создание: `{title,description,user_id}`; передать user_id для автоматической подписки; ответ содержит rss_url и feed_id |
| Пост | `POST /api/channels/{c}/articles` | `{title,text,link?}`; именно **text**, а не summary; после успешного поста статья уже сохранена |
| RSS | `GET /rss/{c}.xml` | Настоящий RSS 2.0 |
| Обновить | `POST /api/refresh` | Ответ `{feeds,new,errors}`; ошибки отдельных источников могут прийти с HTTP 200, показать их из `feeds[].error` |

Пустая лента при отсутствии фильтров — текущее намеренное поведение. Фильтры объединяются
через OR: достаточно одного совпадения; внутри одного keyword-фильтра any/all/none
работают совместно. Подписка ограничивает доступные новости ещё до применения фильтров.

У новости есть `matches` и такой же дублирующий `matched_filters`; выбрать одно поле,
например `matches`, чтобы не рисовать бейджи дважды. Структура причины:

```json
{
  "filter_id": 1,
  "filter_name": "Политика",
  "kind": "topic",
  "details": {
    "score": 0.589,
    "threshold": 0.45,
    "best_phrase": "Политика и международные отношения: правительства, президенты, министры, выборы, санкции, переговоры, дипломатия"
  }
}
```

Для keyword показать `matched`, `absent`, `criteria`, при необходимости `hits/highlights`.
Координаты относятся к тексту после очистки `keyword.clean_text()`, где пробелы и переносы
сжаты. В БД после агрегатора переносы ещё могут быть: для подсветки нельзя автоматически
считать эти строки идентичными. Python считает позиции по Unicode code points, а JS —
по UTF-16; при emoji использовать, например, `Array.from(text)` для работы с координатами.
Сами тексты отображать безопасно через `textContent`; `details.in` может быть строкой
`"title, summary"` или пустой строкой у фильтра только с none.

Подключение SSE:

```javascript
const stream = new EventSource(`/api/users/${userId}/stream`);
stream.addEventListener("refresh", () => reloadNews());
// При смене пользователя/уходе со страницы:
// stream.close();
```

`onmessage` не обработает именованное событие refresh. SSE сообщает об изменении данных,
а не передаёт готовые статьи. Не создавать новое соединение при каждой перерисовке;
не запускать параллельно много одинаковых `/news` при частых событиях.
Ошибки API обычно находятся в `detail`; для ошибок Pydantic это может быть массив.
