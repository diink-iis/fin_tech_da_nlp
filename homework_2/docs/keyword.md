
# Роль 1 — фильтрация по ключевым словам

Модуль: `app/engines/keyword.py`. Тесты: `tests/test_keyword.py`.

## Назначение

`KeywordEngine` получает готовую новость (`Article`) и пользовательский фильтр (`Filter`), определяет, соответствует ли новость фильтру, и возвращает `MatchReason` с техническим объяснением либо `None`. Это ровно интерфейс из `app/contracts.py`; файл контракта не менялся.

Модуль **не** загружает RSS, не обращается к БД, не управляет пользователями и не рисует UI. Это ответственность ролей 3, 4 и 5 соответственно. Один экземпляр `KeywordEngine` подходит для новостей всех пользователей, потому что конфигурация передаётся при каждом вызове `match`.

```
Article + Filter(kind="keyword")
        │
        ├─ проверка params и fields
        ├─ извлечение видимого текста из HTML заголовка/описания
        ├─ разбиение на слова → нормализация → русские леммы
        ├─ поиск слов и последовательностей лемм (фраз)
        ├─ логика: (any: OR) AND (all: AND) AND (none: NOT)
        └─ MatchReason + детали для объяснения/подсветки
            или None
```

## Настройка фильтров

```python
from app.contracts import Article, Filter
from app.engines.keyword import KeywordEngine

engine = KeywordEngine()  # создать 1 раз при запуске API
article = Article(
    id=1, feed_id=1, guid="1", title="Банки России снизили ставки",
    summary="Выдача кредитов растёт", link="https://example.org/1",
)
flt = Filter(
    id=5, user_id=10, name="Новости банков", kind="keyword",
    params={
        "any": ["банк", "финансы"],  # хотя бы одно; необязательно
        "all": ["Россия"],          # все; необязательно
        "none": ["реклама"],        # ни одного; необязательно
        "fields": ["title", "summary"],  # необязательно, это значение по умолчанию
    },
)
reason = engine.match(article, flt)
```

Условия: `(банк ИЛИ финансы) И Россия И НЕ реклама`.

- `any`, `all`, `none` принимают список строк или строку со словами через `,`, `;` или перенос строки.
- Каждый элемент списка может быть **словом** (`банк`) или **фразой** (`машинное обучение`). Фраза — соседние слова в том же поле и в исходном порядке; их формы могут различаться (`машинного обучения`). Части фразы не должны оказаться в разных полях. Знаки пунктуации/дефисы между соседними словами не мешают.
- `fields`: `title`, `summary` или оба (по умолчанию). Слова из группы `all` могут оказаться в разных выбранных полях.
- Регистр, `ё`/`е`, HTML-разметка и частые русские грамматические формы не мешают поиску. Подстроки слов **не** считаются совпадением: `банк` не совпадёт с `банкир`.
- Пустой фильтр не совпадает ни с одной статьёй. Фильтр только с `none` допустим: он означает «все новости, кроме содержащих эти слова»; UI должен обозначить эту особенность.
- `kind="topic"` игнорируется этим движком: для тем существует `SemanticEngine`.

Некорректные типы или неизвестные поля вызывают `KeywordFilterError` — интегратор должен преобразовать его в понятную ошибку в интерфейсе (например HTTP 422), а не считать пустой выдачей.

## Формат объяснения (`MatchReason.details`)

Сохранены поля плана `matched` и `in`; остальные поля расширяют объяснение:

| Ключ | Значение |
| --- | --- |
| `matched` | термины пользователя из `any`/`all`, реально найденные в новости |
| `in` | поля, где найдено совпадение: `title`, `summary`, `title, summary` или пустая строка для только `none` |
| `criteria` | исходные (за вычетом пустых/дублирующихся) условия `any`, `all`, `none` |
| `absent` | слова/фразы из `none`, отсутствие которых подтверждено |
| `hits` | список точных совпадений: `term`, `rule`, `field`, `text`, `start`, `end` |
| `highlights` | не повторяющиеся интервалы `{start, end}` отдельно для каждого выбранного поля |

`start` включительно, `end` не включительно. Индексы относятся к **очищенному тексту** `clean_text(article.title/summary)`, а не к исходному RSS HTML. На стороне браузера индексы указаны в *Unicode code points*, то есть для JS лучше использовать `Array.from(text)` (обычный `slice()` JS работает с UTF-16 и может ошибиться при эмодзи перед совпадением). Для подсветки выводить текст как **текст** (`textContent`), а не вставлять внешнюю RSS-строку в `innerHTML`.

У одного подходящего `Article` может быть несколько `MatchReason` от **разных** фильтров пользователя. Сбор этих причин и логика «прошёл хотя бы один фильтр», равно как и проверка его RSS-подписок, выполняются в бэкенде роли 4.

## Почему именно такая архитектура

1. **Общий контракт и чистый движок**: можно тестировать независимо от RSS, FastAPI, SQLite и HTML. Тот же интерфейс у семантического движка роли 2. Роли 4/5 получают стабильную структуру ответа.
2. **Лемматизация `pymorphy3` для русского языка**: в отличие от точного сравнения или `.lower()` находит `банк` в `банки`, `банков`, `банком`, не требуя нейросети или интернет-сервиса.
3. **Поиск последовательностей лемм**: поддерживает фразы в разных падежах и не путает отдельные слова, разбросанные по новости, с одной фразой.
4. **Явные `any/all/none`**: логика детерминирована и объяснима пользователю/преподавателю. Возвращаем *положительные* и *отрицательные* основания для включения статьи.
5. **Смещения для подсветки** вычисляются сразу во время поиска; UI не должен заново угадывать, что было найдено.
6. **Локальный, ограниченный LRU-кэш** (50 000 форм на экземпляр движка) сокращает повторные морфологические разборы без инфраструктуры или скрытых сетевых запросов.

Для учебного приложения, которое должно запускаться на ноутбуке и пройти live-демонстрацию, это хороший баланс точности, простоты установки и объяснимости; **не универсально лучший подход при миллионах статей**.

## Какие были альтернативы

| Вариант | Почему не выбрали |
| --- | --- |
| `lower() + substring` / регулярные выражения без морфологии | `банк` не найдёт `банков`, возможны ошибки вроде `банк` внутри `банкир` |
| Стемминг (обрезка окончаний) | быстрее, но результат — основа, а не нормальная словарная форма; точность на русских формах и названиях менее предсказуема |
| Только эмбеддинги/нейросеть | уже является задачей роли 2; точное «слово должно быть» и исключения `none` удобнее и надёжнее реализовать правилами |
| PostgreSQL full-text / Elasticsearch / OpenSearch | полезно на больших объёмах, но потребует дополнительной инфраструктуры, настройки словарей и сложнее в локальной приёмке |
| Сразу индексировать все слова в БД | ускорит поиск при очень больших объёмах, но усложнит согласованность при редактировании фильтров; для текущего масштаба сначала достаточно in-memory проверки |

Ограничения: первая интерпретация омонима в `pymorphy3` может быть неверной без контекста; `ё` и `е` сознательно считаются эквивалентными; английские слова сравниваются после case-folding **без английской лемматизации**; движок не понимает синонимы и смысл (это `SemanticEngine`). При большом количестве статей и фильтров можно отдельно кэшировать токены статей или добавить инвертированный индекс, не меняя контракт.

## Запуск тестов

В корне репозитория:

```bash
python -m pip install pymorphy3 pytest
python -m pytest -q tests/test_keyword.py
```

Для полного проекта с семантикой дополнительно нужны зависимости из `requirements.txt`; реальная модель `sentence-transformers` может потребовать предварительного скачивания.

В unit-тестах подставлен маленький лемматизатор, чтобы проверить логику **без** скачивания словаря. Отдельный `test_real_pymorphy3_morphology` автоматически запускается, если установлен настоящий `pymorphy3`. До этого тест считается пропущенным, а не пройденным.

Тестируется: `any/all/none`, русский регистр и формы, границы слов, фразы и их порядок, поля, HTML и `&nbsp;`, объяснения и JSON, координаты подсветки, повторные слова, пустые/неверные фильтры, разные пользователи, кэш, обработка нескольких статей.

## Рекомендации для интеграции

- **Роль 4:** создать один `KeywordEngine()` на процесс; при чтении ленты конкретного пользователя выбрать только его подписанные источники и фильтры, вызывать `.match(article, flt)` для `kind="keyword"`, использовать аналогично `SemanticEngine` для `kind="topic"`; статья показывается, если есть минимум одна причина. Не изменять `app/contracts.py` ради этого движка.
- **Роль 4:** `KeywordFilterError` на сохранении фильтра или во время поиска превращать в понятную ошибку, а не падение сервера.
- **Роль 5:** показать `filter_name`, `criteria`, `matched`/`absent` и `hits`. Для подсветки `highlights` отображать на *очищенных* title/summary; при `none`-only показывать текст «не содержит: ...».
- **Роль 3:** может отдавать `summary` с HTML — наш движок самостоятельно очищает его для поиска; сохранённый оригинал статьи не изменяется.
