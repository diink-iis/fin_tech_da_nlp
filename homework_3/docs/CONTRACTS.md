# Контракты проекта №3

Статус: проект интерфейсов для реализации в первый день. Исполняемого кода пока нет.
Владелец интеграции — участник 5; владельцы предметных схем — участники 1 и 2.
После первого согласования совместимые изменения добавляются через PR в `hw3`.
Изменения обязательных полей согласуются с потребителями, версия схемы повышается.

## 1. Документы и единицы поиска

| Сущность | Обязательные поля и смысл |
| --- | --- |
| `Document` | `doc_id`, `title`, `source_url`, `report_number`, `incident_date`, `report_date`, `language`, `sha256`, `pdf_page_count`, `status="final"` |
| `Page` | `doc_id`, `pdf_page` (с 1), `printed_page` (строка или `null`), `text`, `extraction_method` |
| `Chunk` | `chunk_id`, `doc_id`, `section_path`, `parent_id` (или `null`), `text`, `spans` |
| `SourceSpan` | `doc_id`, `pdf_page`, `start_char`, `end_char` — полуинтервал в нормализованном тексте `Page.text` |
| `RetrievedChunk` | `chunk_id`, `rank` (с 1), `score`, `stage` |

У чанка может быть несколько `SourceSpan`, если он пересекает границы страниц.
Смещения считаются по Unicode code points; после разметки `Page.text` не меняется
без обновления версии корпуса. Изменение чанкинга не должно ломать эталонную разметку.
Ранг и оценка поиска не являются уверенностью в правильности ответа.

`corpus_version` идентифицирует манифест с хешами PDF и версию нормализации страниц;
`index_version` дополнительно фиксирует чанкинг, модель эмбеддингов и параметры индекса.
Один отчёт нельзя дважды учитывать в объёме корпуса из-за повторного скачивания
или включения его же приложений отдельным файлом.

## 2. Пример бенчмарка

Каждая запись `BenchmarkItem` хранит:

| Поле | Назначение |
| --- | --- |
| `id`, `dataset_id`, `split`, `group_id` | Идентификатор, один из D1–D5, `dev/test`, группа связанных вопросов для исключения утечки |
| `question`, `language` | Текст запроса и язык |
| `expected_behavior` | `answer`, `refuse` или `correct_premise` |
| `reference_answer`, `required_facts` | Проверенный эталон и атомарные утверждения/критерии полноты |
| `evidence_groups` | Список обязательных элементов доказательства; у каждого есть допустимые альтернативы `SourceSpan` |
| `task_payload` | D4: события с ID; D5: сравниваемые происшествия и критерии сравнения; иначе пустой объект |
| `reference_structured` | D4: эталонный порядок/допустимые отношения; D5: заполненные поля сравнения; иначе `null` |
| `negative_type`, `unanswerability_reason` | Тип ложной предпосылки/недостатка данных и обоснование; для обычных вопросов `null` |
| `generation_model`, `generation_prompt_version` | Происхождение кандидата; для ручного вопроса допускается `null` |
| `review_status`, `reviewer`, `review_notes`, `corpus_version` | Статус проверки, проверяющий, замечания и версия источников |

У отказного вопроса `evidence_groups` могут быть пустыми, но обоснование отсутствия
ответа обязательно. Отсутствие ответа не устанавливается одним неудачным поиском.
При ложной предпосылке по возможности размечается фрагмент, который её опровергает.

Поля `reference_*`, `required_facts`, `evidence_groups`, `negative_type` и данные
проверки **не передаются ассистентам**. Runner передаёт только `question`, `language`
и публичный `task_payload`. В индекс попадают только документы корпуса.

## 3. Общий интерфейс систем

Целевые интерфейсы в `app/contracts.py`:

```python
class Assistant(Protocol):
    def answer(self, request: QARequest) -> QAResponse: ...

class Retriever(Protocol):
    def search(self, query: str, *, top_k: int,
               filters: dict | None = None) -> list[RetrievedChunk]: ...

class LLMClient(Protocol):
    def generate(self, messages: list[dict], *,
                 model: str, max_output_tokens: int) -> GenerationResult: ...
```

`QARequest`: `request_id`, `question`, `language`, `task_payload`.
Выбор системы и параметры поиска поступают из конфигурации, не из эталонной разметки.

`QAResponse`: `request_id`, `system_id`, `answer`, `structured_answer`, `citations`,
`abstained`, `retrieved_chunks`, `context_spans`, `trace`, `latency_ms`, `usage`,
`error`, `corpus_version`, `index_version`.

- `citations` содержит проверяемые ссылки на `doc_id` и физические страницы PDF,
  привязанные к утверждениям ответа.
- `retrieved_chunks` сохраняет порядок результатов каждого шага; `context_spans`
  показывает, какие фрагменты реально вошли в финальный запрос к LLM.
- `trace` фиксирует подзапросы, решения о повторном поиске и ошибки, но не запрашивает
  и не хранит скрытые рассуждения модели.
- Для B1/B2 поля поиска и контекста — пустые списки; версии корпуса/индекса — `null`.
- `error` отличает сбой запроса от содержательного отказа. Ошибку API нельзя
  записывать как правильное воздержание или незаметно исключать из отчёта.
- `usage` учитывает все LLM-вызовы системы, включая разбиение запроса и проверку контекста;
  неизвестное значение оставляется `null`, а не нулём.

## 4. Артефакты оценки

`run_id` связывает:

1. Конфигурацию запуска: commit, версии корпуса/бенчмарка/индекса, модели и промпты,
   параметры поиска, лимиты контекста/шагов/токенов, время запуска.
2. `predictions.jsonl`: один итоговый ответ на пару `item_id × system_id`, попытки и ошибки.
3. `scores.jsonl`: метрики, пояснения judge, версия judge-промпта и статус проверки.
4. `summary.csv`: строки `system_id × dataset_id`, число заданий, успехов/ошибок,
   применимые метрики, задержка и расход токенов.

Ключ кэша включает версию вопроса, систему, модель, конфигурацию, версии корпуса,
индекса и промптов. Кэш judge дополнительно зависит от ответа, эталона и модели судьи.
Повторный запуск с новой конфигурацией не должен использовать старый ответ.

У метрик сохраняются знаменатель и область применимости. Поиск и качество цитат
для закрытых LLM-бейзлайнов обозначаются `N/A`, а не нулём. На D2 все семь систем
оцениваются по правильности ответа; retrieval-метрики дополнительно доступны RAG.
