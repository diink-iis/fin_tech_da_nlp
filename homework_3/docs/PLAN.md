# Проект №3: «Чёрный ящик». План на неделю и разбиение на 5 человек

Цель — выполнить требования на 10 баллов. К концу дня 4 должна работать обязательная
часть на 6 баллов; дни 5–6 отводим на расширения и итоговую оценку, день 7 — на защиту
и резерв. Это рабочие цели, а не обещание оценки. Условие — в [../TASK.md](../TASK.md).

Статус: планирование. Код, данные и результаты пока не реализованы.
Имена участников пока не назначены; номера ролей определяют зоны ответственности.

## 1. Границы темы и критерии приёмки

**Тема для регистрации:** «Чёрный ящик: QA-ассистент по причинам, хронологии
и выводам расследований авиационных происшествий по официальным отчётам NTSB».

- Фиксированный корпус из 6–8 финальных отчётов NTSB, более 500 страниц PDF суммарно.
  Выбираем документы с извлекаемым текстом и несколько менее известных происшествий.
- Вопросы и ответы на русском, доказательства из англоязычных первоисточников.
- Ответы различают факты, свидетельства, выводы комиссии и оставшуюся неопределённость.
  На вопрос, не разрешимый по корпусу, ассистент сообщает об ограничении.
- Пользователь видит ответ, название отчёта, физическую страницу PDF и фрагмент-основание.
- Интерфейс — Streamlit, одна общая схема запроса/ответа для всех версий.
- Веб-поиск в первой реализации не используем: он усложнит воспроизводимость.
  Две базовые LLM отвечают без корпуса и без поиска.

Исходные кандидаты, уже найденные при выборе темы:

| Отчёт | Проверенный ранее объём PDF | Источник |
| --- | ---: | --- |
| US Airways 1549, AAR-10/03 | 213 страниц | [NTSB PDF](https://www.ntsb.gov/investigations/AccidentReports/Reports/AAR1003.pdf) |
| TWA 800, AAR-00/03 | 341 страница | [NTSB PDF](https://www.ntsb.gov/investigations/AccidentReports/Reports/AAR0003.pdf) |

Участник 1 перепроверяет число страниц скачанных файлов и фиксирует хеши.
554 страницы этих двух кандидатов показывают выполнимость порога, но для разнообразия
вопросов собираем больше отчётов. Читаемость, дубли и релевантность проверяются отдельно.
Занятость темы в таблице преподавателя пока не подтверждена; проверка и регистрация — участник 5.

| Этап | Системы | Датасеты | Что предъявляем |
| --- | --- | --- | --- |
| Обязательные требования, 6 баллов | A1–A3 и B1–B2 | D1–D3 | Приложение, 15 комбинаций «система × датасет», метрики, презентация и демо |
| Дополнительные датасеты, +2 | Все готовые системы | Добавляются D4–D5 | Другие задачи и собственные правила оценки; при пяти системах — 25 комбинаций |
| Дополнительные RAG, +2 | Добавляются A4–A5 | Все пять датасетов | Итоговые 7 систем × 5 датасетов = 35 комбинаций |

Изменение только температуры, `top_k` или размера чанка — эксперимент с настройками,
а не самостоятельный RAG-подход. Не требуется, чтобы сложная версия обязательно
выиграла: нужны честные результаты и объяснение наблюдаемого поведения.

## 2. Архитектура и минимальный стек

```text
PDF NTSB → манифест → страницы/разделы/чанки → локальные индексы
                                                   ↓
Streamlit / benchmark runner → Assistant → retrieval → LLM → ответ + цитаты
                                   └── B1/B2 → LLM без retrieval

Ответы + эталоны → детерминированные метрики / LLM-as-a-judge → таблицы + разбор ошибок
```

Рабочий выбор: Python 3.12, Streamlit, PyMuPDF для текстовых PDF, JSONL для данных,
локальный векторный индекс (например FAISS), BM25 и готовые многоязычные эмбеддинги.
Для A2 — готовый reranker. Генерация через API, один общий клиент с таймаутами,
повторами и кэшем. Обучение собственной модели, отдельный сервер БД и полноценный
GraphRAG в обязательный план недели не входят.

Конкретные model ID, провайдеры, версии зависимостей и бюджет фиксируют участники 3 и 5
в день 1 после проверки доступности. Пример библиотеки выше — вариант реализации,
а не утверждённая зависимость. Новый проект получает собственное окружение и зависимости.

Целевая структура (пока созданы только документы):

```text

    retrieval/           # участник 3: dense/BM25/reranker; 4: иерархическое расширение
    assistants/          # участник 3: A1, A2, B1, B2; 4: A3, A4, A5
    ui.py                # участник 5
  benchmark/             # участник 2: схемы, генерация, проверка, runner, метрики
  prompts/               # генерация/поиск: 3–4; датасеты и judge: 2
  configs/               # версии систем, моделей и экспериментов
  data/                  # manifest, pages, chunks, benchmark/dev и benchmark/test
  results/               # конфигурации прогонов, ответы, оценки, сводные таблицы
```

PDF, модели, индексы и кэши хранятся отдельно от Git; в репозитории — манифесты,
скрипты воспроизведения, проверенные датасеты и компактные результаты. Секреты не коммитим.
Участник 5 добавляет правила исключения и `.env.example` при создании каркаса.

## 4. Семь сравниваемых систем

| ID | Владелец | Алгоритм | Этап |
| --- | --- | --- | --- |
| A1 `dense` | 3 | Векторный поиск по чанкам → ограниченный контекст → ответ с цитатами | Обязательный |
| A2 `hybrid_rerank` | 3 | BM25 и dense → объединение рангов → reranker → ответ | Обязательный |
| A3 `parent_child` | 4, данные от 1 | Поиск по маленьким чанкам → расширение до соответствующих разделов → ограничение бюджета контекста → ответ | Обязательный |
| A4 `multi_hop` | 4 | Разбиение вопроса на 2–3 подзапроса → поиск доказательств для каждого → объединение без дублей → общий ответ | Дополнительный |
| A5 `verified_retrieval` | 4 | Первичный поиск → проверка достаточности доказательств → при необходимости одна переформулировка и повторный поиск → ответ или отказ | Дополнительный |
| B1 `llm_baseline_1` | 3 | Первая LLM без документов, retrieval и веб-поиска | Обязательный |
| B2 `llm_baseline_2` | 3 | Вторая LLM без документов, retrieval и веб-поиска | Обязательный |

A5 — прикладной вариант с проверкой доказательств, а не заявление о точном воспроизведении
исследовательского Self-RAG. Для A4/A5 фиксируем лимиты подзапросов, повторов и токенов.
Не допускаем неограниченных агентных циклов.

У A1–A5 одинаковая генеративная модель, версия корпуса, базовая инструкция ответа
и предел финального контекста. Дополнительные вызовы A4/A5 учитываются в расходе и времени.
Одна из моделей B1/B2 совпадает с генератором RAG, чтобы отдельно увидеть эффект retrieval.
Конкретные две модели выбираются по доступности и бюджету в день 1.

## 5. Пять датасетов и метрики

Рабочий ориентир: **50 test-вопросов и 10 dev-вопросов на датасет**.
Итого обязательная часть — 150 test + 30 dev, полная — 250 test + 50 dev.
Это внутренний целевой размер, не требование преподавателя. Уменьшение при нехватке
времени документируем; несколько перефразировок одного факта не считаем независимыми примерами.

| ID | Задача и разметка | Основные метрики | Владелец |
| --- | --- | --- | --- |
| D1 `factual` | Короткие фактологические вопросы; эталон, атомарные факты, допустимые значения/единицы, источники | Accuracy/EM для однозначных значений; полнота и правильность фактов для текстовых ответов | 2 + проверка всеми |
| D2 `evidence_retrieval` | По формулировке обстоятельства найти нужные доказательства среди похожих отчётов; ответ и группы релевантных фрагментов | Правильность ответа для всех систем; Recall@k, MRR@k и покрытие доказательств финальным контекстом для RAG | 2 + 1 |
| D3 `unanswerable` | Вопросы без ответа в корпусе, ложные предпосылки и ответные контрольные вопросы; ожидаемое поведение и обоснование | Правильность выбора «ответить/отказаться/исправить предпосылку»; precision/recall отказа; доля неподтверждённых утверждений; ложные отказы на контролях | 2 + проверка всеми |
| D4 `timeline` | Восстановить порядок заданного набора событий с ID и источниками; неоднозначные пары исключить или явно разметить | Точное совпадение порядка; доля верно упорядоченных сравнимых пар; корректность доказательств | 2 + 1, дополнительный |
| D5 `cross_case` | Сопоставить два происшествия по явно заданным полям; эталон содержит выводы по обоим отчётам | Полнота и правильность полей; поддержка сравнительных выводов; покрытие доказательствами обоих отчётов | 2 + 4, дополнительный |

D4 требует структурированного упорядочивания, D5 — сравнения нескольких документов;
это дополнительные задачи, а не новые названия для D1. D3 содержит и вопросы,
на которые можно ответить, чтобы постоянный отказ не давал высокий результат.

### Как готовим и проверяем

1. LLM генерирует кандидатов только по известным фрагментам; хранится версия промпта.
2. Человек проверяет вопрос, эталон, полноту условий, страницу и перевод терминов.
   Негодные примеры и причины отклонения остаются для презентации.
3. Утверждение «в корпусе нет ответа» проверяется по нескольким поисковым формулировкам
   и вручную; одного промаха текущего retriever недостаточно. Спорные вопросы исключаются.
4. Похожие вопросы об одном факте/эпизоде имеют общий `group_id` и не пересекают dev/test.
   Все системы используют один и тот же test-набор; эталоны не включаются в запрос или индекс.
5. Настройки подбираются на dev. После фиксации test финальные версии оцениваются без
   подбора промптов по его ответам. Если обнаружена ошибка разметки, выпускается новая
   версия бенчмарка с журналом исправлений и повторной оценкой всех затронутых систем.

### Как считаем

- Разметка поиска привязана к страницам и текстовым диапазонам, не к конкретному чанкингу.
  Дубли чанков с одним доказательством не увеличивают Recall. Для разных размеров контекста
  дополнительно сообщаем покрытие доказательств при общем лимите токенов.
- EM, нормализация чисел/единиц, порядок событий и retrieval-метрики считаются кодом.
  Для открытых ответов judge получает вопрос, эталон, доказательства и анонимизированный ответ.
- Judge оценивает отдельно правильность, полноту и неподтверждённые утверждения,
  возвращает структурированный результат с пояснениями. Текст источника считается данными,
  а не инструкцией. Промпт и модель судьи сохраняются; предпочтительна модель,
  отличающаяся от генератора, если позволяет бюджет.
- До полного запуска сравниваем judge с ручной оценкой на 20–30 dev-ответах,
  разбираем расхождения. Судья не заменяет ручную проверку эталонов.
- B1/B2 проходят все пять задач по качеству ответа. Retrieval-метрики и верность цитат
  у них `N/A`, поскольку им не выдаются документы. Фактологичность и галлюцинации
  проверяются по тем же эталонам; отсутствие цитаты само по себе не означает галлюцинацию.
- Для каждого запуска сохраняем ошибки, долю успешных ответов, задержку и токены.
  Ошибки не скрываем: качество на успешных ответах публикуется вместе с покрытием,
  а доля корректных ответов на все задания считает сбои неуспехом.
- Сводная таблица содержит размеры выборок и метрики по каждому датасету,
  без необоснованного усреднения несопоставимых шкал в один «общий балл».
